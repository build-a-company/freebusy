## Services

### RatePlanService

RatePlanService manages what a bookable resource costs.  Rate plans are the money half of the engine, and the half no RFC covers. They attach to an RFC 9073 VRESOURCE by reference rather than living on it, so the standards-defined description of a bookable thing never grows a price.

| Method | Request | Response | Description |
| --- | --- | --- | --- |
| `GetRatePlan` | `GetRatePlanRequest` | `RatePlan` | Retrieves one rate plan. |
| `ListRatePlans` | `ListRatePlansRequest` | `ListRatePlansResponse` | Lists rate plans, most usefully filtered by the resource they price. |
| `CreateRatePlan` | `CreateRatePlanRequest` | `RatePlan` | Creates a rate plan. |
| `UpdateRatePlan` | `UpdateRatePlanRequest` | `RatePlan` | Updates a rate plan.  Editing a plan changes what future quotes cost; it does not reprice a booking already taken, which carries the components it was quoted under. |

### QuoteService

QuoteService prices a window without reserving anything.  Read-only and side-effect free: a quote is an answer, not a claim. Reserving is HoldService's job, and the two are separate calls precisely so a caller can show a price before committing to inventory.

| Method | Request | Response | Description |
| --- | --- | --- | --- |
| `ComputeQuote` | `ComputeQuoteRequest` | `ComputeQuoteResponse` | Prices a window under a rate plan, returning every component.  A custom method (AIP-136): it computes a result rather than fetching a resource, so it takes neither a standard-method name nor its shape.  An invalid promotion code is reported in rejected_promotion_codes rather than failing the call — a mistyped code should re-render a price, not an error. |

## Messages

### RatePlan

A RatePlan is what a bookable resource costs: a base price, the calendar of overrides that move it, and the fees and taxes layered on top.  Native, with no RFC behind it, and this is the one gap the audit could not close. The IETF has never standardised commerce — RFC 8905's `payto:` names a payment *address*, not an amount — so while every statement this engine makes about time comes from a published RFC, every statement it makes about money is ours. `google.type.Money` carries the amounts, which is the closest thing to a standard available and is exempt from the cross-package rule.  A resource of its own rather than fields on the thing being priced: the same resource is sold at different rates to different channels and seasons, a rate plan is edited on a cadence entirely unlike the resource's, and a booking must still be explainable under the plan that priced it long after that plan stops being offered. Pricing attaches to a resource by reference, so an RFC 9073 VRESOURCE stays a description of a bookable thing and never grows a price.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `name` | `string` | `IDENTIFIER` | The rate plan name. Format: ratePlans/{rate_plan} |
| `resource` | `string` | `REQUIRED` | The bookable resource this plan prices. Format: resources/{resource} |
| `display_name` | `string` | `REQUIRED` | Human-friendly name, e.g. "Flexible", "Non-refundable", "Early Bird". |
| `description` | `string` | `OPTIONAL` | Free-form description shown with the offer. |
| `price` | `Money` | `REQUIRED` | The default price, interpreted per `pricing_unit`. Overrides in `rate_overrides` replace it where they match; this applies where none do. |
| `pricing_unit` | `PricingUnit` | `OPTIONAL` | What `price` is charged per. Defaults to per booking. |
| `rate_overrides` | `repeated RateOverride` | `OPTIONAL` | The rate calendar: date- and weekday-scoped replacements for `price`. Later-listed overrides win where two match the same date. |
| `los_discounts` | `repeated LosDiscount` | `OPTIONAL` | Discounts applied once a stay reaches a minimum length. The most generous matching discount applies; they do not stack. |
| `fees` | `repeated Fee` | `OPTIONAL` | Fees added on top of the base subtotal. |
| `taxes` | `repeated Tax` | `OPTIONAL` | Taxes applied to the taxable base — the subtotal plus every fee marked taxable. |
| `dynamic_rules` | `repeated DynamicRule` | `OPTIONAL` | Rules that move the price by the state of the world rather than by the calendar — occupancy, lead time, length of stay. Empty means static pricing, which is the default and stays a first-class choice.  Every matching rule applies, in order, each compounding on the running price. That is a deliberate choice over "most specific wins": revenue management is genuinely multiplicative — a last-minute booking into a nearly-full house is both — and a winner-takes-all rule would silently discard one of the two signals. |
| `bounds` | `PriceBounds` | `OPTIONAL` | Hard bounds on any computed price. Strongly recommended once `dynamic_rules` is non-empty.  Compounding rules multiply, and multiplication runs away: three rules at +25% each is +95%, not +75%, and a mispriced band is discovered by a guest rather than by a test. Bounds are the blast radius — they cap what any arithmetic error can charge, and floor what a stacked discount can give away. |
| `state` | `RatePlanState` | `OUTPUT_ONLY` | Lifecycle state. New plans start ACTIVE. |
| `create_time` | `Timestamp` | `OUTPUT_ONLY` | Creation timestamp. |
| `update_time` | `Timestamp` | `OUTPUT_ONLY` | Last-modification timestamp. |
| `etag` | `string` | `OUTPUT_ONLY` | Opaque version for optimistic concurrency (AIP-154); echo on update/delete. |

### DynamicRule

A rule that moves price according to something measured at quote time.  Bands are evaluated against the trigger's measured value and at most one band matches per rule, because bands of a single rule partition a range. Rules compound across triggers; bands do not compound within one.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `trigger` | `DynamicTrigger` | `REQUIRED` | What this rule measures. |
| `bands` | `repeated DynamicBand` | `REQUIRED` | The ladder. Overlapping bands are a configuration error: the first match in declaration order wins, so an overlap silently makes a later band dead rather than failing, and a quote is the wrong place to discover that. |

### DynamicTrigger

What a DynamicRule reads to decide whether it applies.  Each trigger measures something the calendar cannot: RateOverride already moves price by date and weekday, so these are deliberately the levers that depend on the state of the world at quote time rather than on when the stay falls.

| Value | Number | Description |
| --- | --- | --- |
| `DYNAMIC_TRIGGER_UNSPECIFIED` | 0 | Unset; the rule is ignored rather than guessed at. |
| `DYNAMIC_TRIGGER_OCCUPANCY` | 1 | Percentage of the resource pool already taken across the window, 0-100. The yield lever: price rises as the last units go. |
| `DYNAMIC_TRIGGER_LEAD_TIME` | 2 | Whole days between the quote and the window's start. The booking-curve lever: early-bird discounts and last-minute pricing are the same rule with the sign flipped. |
| `DYNAMIC_TRIGGER_LENGTH_OF_STAY` | 3 | Nights in the window. Distinct from LosDiscount, which only ever discounts and never stacks; a length band here can move price either way and composes with the other triggers. |
